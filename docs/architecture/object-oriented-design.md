# オブジェクト指向設計・検証基準

## 目的

個別プロジェクトで、ドメイン上の不正な値、異なる概念の混同、意図しない状態変更を設計段階から防ぐ。この文書だけで設計・実装・レビュー・テストを再現できるようにする。外部記事やURLの参照は前提としない。

## 設計基準

### 1. ドメイン概念を型として表す

- メールアドレス、金額と通貨、識別子、期間など、独自の制約や意味を持つ値をプリミティブ型のまま受け渡さない。
- 値オブジェクトは生成時に全ての不変条件を検証する。無効な値のインスタンスは作成できない。
- 正規化が必要な値は生成時に一度だけ正規化する。
- 同じ意味を持つ値オブジェクト同士は、保持する値で比較できるようにする。

### 2. 生成後の状態変更を防ぐ

- 値オブジェクトに公開setterを持たせない。
- 可変な配列、オブジェクト、日付などを内部に保持する場合は、生成時と公開時に防御的コピーまたは不変化を行う。
- 状態を変える必要がある操作は、既存の値を変更せず、新しい有効な値オブジェクトを返す。
- 読み取り専用の操作は、状態を変更しない。

### 3. 状態変更を明示する

- 状態を変更する操作（コマンド）と、値を返すだけの操作（クエリ）を分ける。
- コマンドは入力を境界で検証し、許可された状態遷移だけを実行する。
- クエリはデータ取得・整形以外の副作用を持たない。
- 状態変更の結果は、成功・失敗と理由を呼び出し側が判定できる形で返す。

### 4. 責務と依存を小さく保つ

- 一つのクラスまたはモジュールは、一つの変更理由に集中させる。
- `is-a` が成立しない関係に継承を使わない。部品の組み合わせにはコンポジションを使う。
- 可変な規則や外部サービスは、必要な能力だけを表す小さな抽象に依存させる。
- 具体実装の選択と組み立ては外側で行い、ドメインモデルへ永続化・UI・ネットワークの詳細を持ち込まない。
- 抽象を実装する型は、同じ入力条件・出力・副作用の契約を守る。

## 実装時の確認項目

- 境界入力は、利用前に値オブジェクトまたは検証済みの型へ変換されている。
- 不正な値、異なる単位・通貨・識別子の混同、許可されない状態遷移を表す処理がない。
- 呼び出し側が内部状態を変更できる参照を受け取らない。
- 変更し得る振る舞いは条件分岐の追加ではなく、明示的な差し替え可能なオブジェクトとして扱われている。
- UI、API、永続化の都合による型や例外がドメイン層へ漏れていない。

## 必須テスト

各ドメイン概念の変更時には、少なくとも次を自動テストで確認する。

1. 有効な入力からだけインスタンスを生成できる。
2. 無効な入力では生成またはコマンドが失敗し、状態は変わらない。
3. 同じ値は等しく、異なる値は等しくない。
4. 生成後に公開API・内部の可変値・取得した値を経由して状態を変更できない。
5. 許可された状態遷移は成功し、許可されない遷移は失敗する。
6. クエリを実行しても状態が変わらない。
7. 差し替え可能な実装は共通の契約テストを満たす。

## 個別プロジェクトへの適用手順

1. 対象ドメイン、変更対象、非対象、既存の利用箇所を特定する。
2. 現在の振る舞いをテストで固定し、移行後の不変条件と状態遷移を明文化する。
3. 境界から値オブジェクトを導入し、既存APIへの影響を小さく保つ。
4. 上記の必須テスト、型検査、Lint、既存の回帰テストを実行する。
5. 未検証範囲と互換性上の判断を記録し、人間が受け入れ判断を行う。

## 同期方針

この基準は、学習完了後に個別プロジェクトへコピーまたはそのプロジェクト固有の規約へ統合できる。同期前に対象・適用範囲・受け入れ条件を人間が承認し、プロジェクト固有の技術・既存仕様と矛盾する箇所は調整する。外部記事本文・アクセストークン・環境固有の設定は同期しない。
